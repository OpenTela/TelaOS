# Simulator v0.9

Настоящая прошивка TelaOS на ПК: тот же `src/`, LVGL 9.2 из `lib/lvgl`, `include/lv_conf.h`,
шрифты, Lua, `data/`. Окно, где мышь — палец; робот, который тапает и проверяет; скриншоты
каждого экрана каждого приложения — и их сравнение в каждом PR, картинками и словами.

## Changelog

- **v0.9**: Судья — Chromium: `sim/tools/judge.py` раскладывает страницы `html_tags` в Chromium и сверяет
  рамки элементов с часами; в отчёте PR — совместимость. Робот пишет в `tree` и элементы приложения
  с рамками их объектов (`"dom"`).
- **v0.8**: Картинки слитого PR остаются в ветке `sim-screens`: его комментарий и после слияния
  показывает, что изменилось. Удаляются только картинки PR, закрытого без слияния.
- **v0.7**: Деревья виджетов сравниваются на всех экранах, а не только на изменившихся: если пиксели те же,
  а дерево другое (у элемента другой id, появился элемент за краем), отчёт PR пишет это в разделе
  «Изменилось незаметно».
- **v0.6**: Видимый текст контейнера: слова одной строки HTML идут слитно, как на экране
  (`H<sub>2</sub>O` — «H2O», а не «H 2 O»).
- **v0.5**: Случайные страницы: `sim/tools/gen_pages.py` пишет приложения со случайной разметкой,
  `sim/tools/sim_pages.py` рисует их базой и PR-ом; в отчёте PR — что изменилось и какие страницы
  нестабильны.
- **v0.4**: Честная память: кучи часов (DRAM и PSRAM) на том же TLSF, что в ESP-IDF; `malloc`/`new`
  прошивки по правилам Arduino-ESP32. Память каждого экрана в отчёте PR, у робота `mem` и
  `expect mem.*`, ключи `--dram-kb` / `--psram-kb`.
- **v0.3**: Счётчик «сишных» мест: `sim/tools/code_meter.py`, в отчёте PR — сколько их было
  и стало в `src/`.
- **v0.2**: Изменения словами: `sim/tools/tree_diff.py` сравнивает деревья виджетов «до» и
  «после», в отчёте PR — раздел «Что изменилось». В дереве `tree` — id, которые элементам дал
  автор приложения.
- **v0.1**: Симулятор в репозитории (`sim/`), робот, скриншоты всех страниц всех приложений,
  проверка PR в GitHub Actions: TelaCI + экраны «до / после / разница» комментарием в PR.

## Сборка и запуск

Ubuntu 24.04: `sudo apt install cmake ninja-build libsdl2-dev libpng-dev libmbedtls-dev`

```bash
cmake -S sim -B build/sim -G Ninja && cmake --build build/sim
build/sim/telaos_sim                                                  # окно, мышь = палец
build/sim/telaos_sim --zoom 2                                         # окно крупнее
build/sim/telaos_sim --headless --script sim/tests/tela_hello.sim --out shots
```

| Ключ | Что делает |
|------|-----------|
| `--headless` | без окна: время идёт так быстро, как считает процессор |
| `--script <file>` | сценарий робота (можно несколько) |
| `--run "<команды>"` | команды робота прямо в строке, через `;` |
| `--out <dir>` | куда класть скриншоты и деревья (`shots`) |
| `--data <dir>` | что «прошить» в LittleFS (по умолчанию `data/`) |
| `--extra-data <dir>` | дописать поверх: приложения-образцы для тестов (`sim/tests/fixtures`) |
| `--dram-kb <n>`, `--psram-kb <n>` | сколько DRAM и PSRAM у прошивки (по умолчанию — оценка, см. «Память часов») |

Прошивка не меняется ни на байт. Симулятор подставляет только то, что на часах дают плата
и ядро Arduino:

| Часы | Симулятор |
|------|-----------|
| Плата (`Device::inst()`) | `sim_tela_device.cpp`: вывод и касания → виртуальная панель |
| `millis()` / `delay()` | виртуальные часы; `time()` тоже, старт 2026-10-30 10:09:30 UTC |
| LittleFS, залитый из `data/` | `data/` (+ `--extra-data`) в LittleFS из TelaCI при старте |
| Диск LVGL `C:` (`/littlefs`) | `sim_tela_fs.cpp`: тот же `lv_fs_stdio_init()`, но поверх LittleFS |
| Serial-консоль | ввод робота: `> app launch hello` |
| Куча: DRAM и PSRAM | `sim_heap.cpp`: две кучи на TLSF из ESP-IDF, с настоящими отказами (см. «Память часов») |
| ESP, NimBLE, FreeRTOS | заглушки TelaCI (`ci/stubs`) |

Время виртуальное, поэтому скриншоты детерминированы: одинаковая прошивка даёт побайтно
одинаковые PNG.

## Робот

Сценарий — команда на строку (или через `;`), `#` — комментарий. Цель — один токен:
`@id` (элемент по id), `@id:0.9,0.5` (точка внутри), `"текст"` (видимая надпись, абзац,
клавиша, строка списка), `x,y` (пиксели).

```
> app launch hello                         # консоль прошивки — та же, что по Serial и BLE
> ui type stdin Анатолий
tap "Run"                                  # палец на панели
expect $_stdout contains "Thank you, Анатолий"
expect @dlg :hidden                        # скрыт или прокручен за край
expect @card contains "text"               # у контейнера — видимый текст внутри
shot tela_03_result
```

| Команда | Что делает |
|---------|-----------|
| `wait <ms>` | подождать (виртуальные мс) |
| `tap`, `longpress <T> [ms]`, `drag <T1> <T2> [ms]`, `press`, `move`, `release` | палец |
| `scroll @id` | прокрутить к элементу |
| `text @id <value>` | вписать текст в поле |
| `expect @id <value>`, `expect @id contains <v>` | значение виджета; числа — диапазоном `20..30`. У контейнера — видимый текст: надписи по порядку через пробел, слова одной строки HTML — слитно |
| `expect <@id или "текст"> :visible` / `:hidden` | виден ли на экране |
| `expect $var <value>` | переменная состояния приложения |
| `expect mem.<число> <value>` | память часов: `dram_` или `psram_` + `free`, `min_free`, `largest`, `total`, `blocks`, `failed` |
| `mem` | память часов — в лог |
| `> <строка>` | строка в консоль прошивки |
| `shot <name>`, `tree <name>` | PNG экрана; JSON дерева виджетов с рамками, значениями, переполнением, id элементов и памятью часов, и элементы приложения, как их видит скрипт, — с рамками их объектов (`"dom"`) |

Тап по закрытому виджету проваливается (`covered by …`) — как промахнулся бы настоящий палец.
Сценарии лежат в `sim/tests/*.sim`, приложения-образцы для них — в `sim/tests/fixtures/apps/`.

## Экраны всех приложений

```bash
python3 sim/tools/sim_screens.py --head . --base ../telaos-future --out build/screens
```

Собирает симулятор из `sim/` против обеих копий прошивки, на каждой снимает лаунчер и каждую
страницу каждого приложения (список берёт у самой прошивки — вместе с нативными и образцами),
прогоняет `sim/tests/*.sim` на `--head`, сравнивает экраны попиксельно и пишет:

| Файл | Что |
|------|-----|
| `report.md` | отчёт: что изменилось — словами и картинками, тесты робота |
| `publish/before`, `after`, `diff` | только изменившиеся экраны; на `diff` новый экран серым, изменённые пиксели — пурпурным, вокруг — жёлтая рамка |
| `status.json` | то же для машин; у изменившегося экрана — `changes`, те же слова; `unseen` — изменившиеся незаметно |
| `shots-base/`, `shots-head/`, `tests/` | всё целиком: PNG и дерево виджетов (JSON) каждого экрана |
| `judge.json` | судья: каждый элемент страниц `html_tags` — рамка на часах и в Chromium (см. «Судья: Chromium») |

Без `--base` — просто снимки всех экранов. Только стандартная библиотека Python.

### Что изменилось — словами

Рядом с каждым снимком робот сохраняет дерево виджетов. У изменившегося экрана
`sim/tools/tree_diff.py` сравнивает деревья «до» и «после» и пишет, что заметит человек:

```
- Надпись: «The Cubic» → «Кубик»
- Появилась надпись `#hint` «Нажми кнопку»
- Кнопка «БРОСИТЬ» сдвинулась на 38 px вниз
- Кнопка «БРОСИТЬ»: ширина 336 → 384
- Блок `#lists` не помещается по высоте: +12 px
- Экран был пуст — появилось 10 элементов, в том числе «РАБОТА», «25:00», «Session 1 of 4»
```

Элементы сопоставляются по типу, id и тексту, поэтому вставленный элемент не «сдвигает»
остальные. Что едет вместе с родителем, не повторяется; соседи, сдвинутые на одно и то же,
идут одной строкой; если у элемента остались на месте начало, середина или конец, он не
сдвинулся, а изменил размер; скрытое и до и после не считается. Не больше 8 строк на экран,
остальное — числом. Если деревья совпали, а пиксели нет: «Виджеты те же — изменились только цвета, шрифты
или картинки». Если наоборот — пиксели те же, а деревья нет, — экран идёт в раздел «Изменилось незаметно»:
так видно, например, что у элемента сменился id, по которому его находит скрипт. Одни и те же деревья
всегда дают одни и те же слова. Вручную:
`python3 sim/tools/tree_diff.py before.json after.json`. Тесты:
`python3 -m unittest discover -s sim/tools -p 'test_*.py'`.

### Сколько в коде осталось C

Рефакторинг ведёт код от C на сырых указателях к типизированному C++. `sim/tools/code_meter.py`
считает в `src/` то, что типы заменяют: `strcmp` и его родню, `strstr`/`strchr`, `snprintf`,
`strcpy`/`strcat`, буферы `char x[N]`, голые `malloc`/`free`. Комментарии и строки не считаются,
шрифты (`src/font/*.c`) — тоже. В отчёте PR одна строка:

```
Сишные места в src/: 451 → 437 (−14): `strcmp` −10, `char x[N]` −4
```

Вручную: `python3 sim/tools/code_meter.py <checkout> [<база>]` — плюс самые «сишные» файлы.

## Память часов

У часов две кучи: внутренняя DRAM (быстрая, её мало) и PSRAM (8 МБ, медленнее). Прошивка видит
их так, как их показывает ESP-IDF, — и симулятор держит такие же две кучи (`sim/sim_heap.cpp`)
на том же распределителе TLSF, на котором построена куча ESP-IDF (`sim/third_party/tlsf`):

| Что выделяет прошивка | Куда, как на часах |
|---|---|
| `heap_caps_malloc(n, …INTERNAL)` | только DRAM |
| `heap_caps_malloc(n, …SPIRAM)`, `ps_malloc` | только PSRAM |
| `heap_caps_malloc(n, …8BIT / DEFAULT)` | DRAM, если нет места — PSRAM |
| `malloc`, `new`, `std::string` до 4 КБ | DRAM, потом PSRAM (Arduino-ESP32: `SPIRAM_MALLOC_ALWAYSINTERNAL=4096`) |
| `malloc`, `new` больше 4 КБ | PSRAM, потом DRAM |

Не влезло — выделение не удаётся, как на часах, и прошивка идёт своим путём: например, при
DRAM меньше 50 КБ `memory_manager` уменьшает буфер экрана. `ESP.getFreeHeap()`, `sys info`,
логи `[Heap] …` показывают модель. `malloc`/`new` считаются только пока работает прошивка
(`setup()`, `loop()`); окно, робот и PNG симулятора живут в куче ПК.

В дереве каждого экрана (`tree`) — `"mem"`: всего, свободно, самое низкое с загрузки,
крупнейший свободный блок, сколько блоков и сколько отказов. Отчёт PR пишет экран, где DRAM
оставалось меньше всего, отказы и экраны, где расход изменился на 1 КБ и больше:

```
Меньше всего DRAM оставалось на excel · main: 38,6 КБ (до: 38,6 КБ)
```

**Размеры — пока оценка** (DRAM 320 КБ, PSRAM 8 МБ). Сверка — по логу настоящих часов:
`[Heap] Before Display` (столько DRAM у прошивки до первого выделения) и `sys info` в лаунчере
и в приложениях; их числа ставятся ключами `--dram-kb` / `--psram-kb`. Пока не учтено:
указатели на ПК 8-байтные, поэтому структуры больше, чем на часах (дальше — 32-битная сборка);
резерв DRAM под DMA (`SPIRAM_MALLOC_RESERVE_INTERNAL`); выделения до `setup()`. Тесты модели:
`sim/tools/test_sim_heap.py` (собирает и запускает модель и TLSF).

## Случайные страницы

32 экрана — это разметка, которую кто-то написал. Чтобы проверить движок и на той, что никто не
писал, `sim/tools/gen_pages.py` сочиняет приложения по одной странице. Страница N при одном и том же
`--seed` всегда одна и та же. На страницах:
- все теги, которые знает движок (таблица слоя HTML и теги TelaOS — тест проверяет по исходникам);
- привязки `{count}` и незаданная `{nothing}`, `<style>`, `@for`, шаблоны обеих версий;
- то, что разбор должен пережить: комментарии с `>`, потерянные и лишние закрывающие теги, `<li>`
  без `</li>`, одиночный `<`, теги в верхнем регистре, перевод строки внутри тега, атрибут без
  значения перед другими.

`sim/tools/sim_pages.py` рисует каждую страницу базой один раз и PR-ом дважды. Если PR нарисовал
страницу по-разному в двух запусках, она нестабильна: читает память, в которую никто не писал, или
зависит не от страницы. Остальные сравниваются с базой по дереву виджетов (словами, как экраны) и по
пикселям. В отчёте PR (`sim_screens.py --pages 300`) одна строка, если ничего не изменилось:

```
**Случайные страницы:** 300 из 300 без изменений (`gen_pages.py --seed 1`)
```

Иначе — что изменилось на каждой странице, нестабильные и те, что не нарисовались. Посмотреть
страницу: `python3 sim/tools/gen_pages.py <папка> --count 300 --seed 1` — она в
`<папка>/batch_K/apps/gen_NNNN/`. Вручную, двумя готовыми симуляторами:
`python3 sim/tools/sim_pages.py --base-sim A --head-sim B --out <папка>`.

## Судья: Chromium

Совместимость — доля элементов, у которых рамка (x, y, ширина, высота) совпала с Chromium в
пределах ±2 px. `sim/tools/judge.py` считает её на страницах приложения-образца `html_tags`:
- Chromium без окна (Playwright) раскладывает каждую страницу: та же разметка, шрифты часов (Ubuntu
  в четырёх начертаниях), окно — экран симулятора. `{var}` — значение по умолчанию из `<state>`;
  то, что на часах значит CSS, отдаётся как CSS: `w` и `h` — `width` и `height`, `visible="false"` —
  `hidden`;
- робот пишет в `tree` и элементы приложения, как их видит скрипт (`"dom"`), — с рамкой объекта
  каждого;
- элементы сопоставляются по месту в дереве: дети — по тегу и по порядку. Если на часах нет
  обёртки (`<tbody>`, `<picture>`), её дети ищутся уровнем выше;
- не считаются текст в строке (`<b>`, `<a>` в абзаце — на часах у него нет своей рамки) и то, что
  не показывает ни один из двух. Страница `icons` не судится: у Chromium нет шрифта Material Symbols,
  он нарисовал бы иконки чужим.

В отчёте PR:

```
**Совместимость с Chromium:** html_tags, рамки элементов ±2 px — **0 из 153, 0%**
- По отдельности, из 148 рамок: x 73% · y 5% · ширина 62% · высота 11%
- Высота на часах больше на 3 px — у 69
```

Ещё — какие элементы стали совпадать и какие перестали, а под катом каждое несовпадение:
«`text` · `h2#h2`: y 8 → 20, высота 36 → 28» (часы → Chromium). Всё целиком — `judge.json`.
Вручную, по снимкам `sim_screens.py`:

```bash
pip install playwright==1.63.0 && python3 -m playwright install chromium
python3 sim/tools/judge.py --app sim/tests/fixtures/apps/html_tags --shots build/screens/shots-head --all
```

CI ставит ту же версию Playwright — и тот же Chromium в каждом прогоне. Шрифты часов лежат прямо
в странице (`data:`), а не рядом с ней файлами, и рисуются без хинтинга (`--font-render-hinting=none`):
высота строки — та, что у шрифта, а не та, что просит fontconfig машины. С хинтингом строка 16px
Ubuntu на GitHub выходит 20 px, а без него — 18, как у браузера на Mac и Windows. Без Playwright — или если Chromium не запустился или
не загрузил шрифты — отчёт пишет «не измерена» и почему: число на чужом шрифте не было бы числом.

## Проверка PR

`.github/workflows/pr-checks.yml`, на каждый PR:

1. **TelaCI** — `ci/build.py --mock` и `ci/test.py`, плюс тесты `sim/tools` (так же и на push
   в `main`/`future`).
2. **Simulator screens** — `sim_screens.py --pages 300` против базы PR, с судьёй (Chromium из
   Playwright 1.63.0). Картинки уходят в ветку
   `sim-screens` (`pr-<номер>/<sha>/`, один коммит без истории — картинки прошлых прогонов не копятся),
   отчёт — одним комментарием в PR, который обновляется с каждым пушем. Слили PR — картинки
   остаются, закрыли без слияния — удаляются. Упал тест робота или PR не собирается — проверка
   красная.

PR из форков получают тот же отчёт в сводке job и в артефакте `sim-screens`, без картинок
в комментарии: у их токена нет права писать.

## Ограничения

- Сеть (BLE-мост, `fetch`) не эмулируется: такие экраны показывают «нет связи».
- Экран 480×480 (esp4848s040); другие платы — `-DTELA_SCREEN_W/H`.
- Скорость часов не эмулируется: в `--headless` всё мгновенно, в окне — в реальном времени.
- Память часов — модель с оценочными размерами, пока не сверена с часами (см. «Память часов»).
- Собирается на Linux (и WSL): время подменяется ключом компоновщика GNU `--wrap=time`, у macOS
  такого нет.
